# 下一版本功能建议（v0.2 提案）

- 日期：2026-11-03
- 依据：v0.1 功能开发完成后的实际缺口、已知问题清单（KI-01~KI-24）、以及本轮"模板空槽位"反馈暴露出的交互模式
- 原则：**只提能在 2~3 周内交付、且用户能感知到的改动**；纯架构重构不单列（除非它挡住上面这些）

## 一、先判断：v0.1 真正的短板在哪

v0.1 能完成"导入 → 排版 → 导出"的完整链路，但离"天天用"还差三类东西：

| 短板 | 具体表现 | 影响 |
| --- | --- | --- |
| **精细操作不足** | 只能拖鼠标或改右侧数值，没有方向键微调；改 1px 要开面板 | 排版拼图对像素位置敏感，这是高频动作 |
| **重复劳动** | 每张新图都要"选中 → 填空 / 拖入"；同一张图想放两格要绕路 | 9 宫格、12 格场景下很磨人 |
| **出错后难以自证** | 没有本地日志；导出失败只能看到一句提示 | 用户和我都缺少排查依据 |

所以下一版建议**不做大功能**（文字、贴纸、滤镜这类会显著扩大测试面），而是把"精细操作 + 批量效率 + 可诊断性"补齐。

## 二、建议纳入 v0.2 的 6 项

按"用户价值 ÷ 实现成本"排序。

### 1. 方向键微调（强烈建议）

- **行为**：选中实例后 `↑↓←→` 移动 1px，`Shift+方向键` 移动 10px；`Ctrl+方向键` 改尺寸 1px
- **理由**：这是排版类工具的基本盘。当前要精确移动 1px 必须打开右栏改数值，打断了"看画布调整"的节奏
- **成本**：小。走 `commit` + `mergeKey`（连续按方向键合并为一步撤销），复用现有 `updateInstance`
- **风险**：需处理输入框焦点（现有 `isEditable` 判定可复用）

### 2. 连续填图流（强烈建议，直接延续本轮反馈）

- **行为**：双击资源库图片填入下一个空槽位后，**自动选中刚填充的槽位并高亮编号**；再双击下一张继续填，不需回头找空格
- **配套**：资源库列表按"尚未放入画布"优先排序的开关（一眼看出还有哪些图没用上）
- **理由**：本轮已实现"按编号顺序填空"，但用户仍要自己记住填到第几格；把"下一格是谁"变成界面状态，9 宫格体验会明显不同
- **成本**：小。状态放 `viewStore`，不改文档模型

### 3. 撤销历史面板

- **行为**：右栏新增"历史"页，列出最近 50 步（"拖动图片""裁切""应用模板：九宫格"…），点击任意步直接跳回该状态
- **理由**：快照式历史栈已经存在，`past[].label` 也已写好，**只差一个列表 UI**；对"试了十种布局想回到第三种"这类场景价值很高
- **成本**：小~中。需要给 `history` 增加"跳到第 n 步"的纯函数 + 测试
- **注意**：跳转本身也应是可撤销操作，不能破坏现有 redo 语义

### 4. 自定义模板（保存当前布局）

- **行为**：「模板」页底部加"把当前布局存为模板"，保存单元格矩形与间距；可命名、可删除，存本地配置
- **理由**：20 个内置模板覆盖不了所有场景，用户一旦调出顺手的布局，下次想复用只能重来
- **成本**：中。数据结构简单（归一化矩形数组）；难点在"从实例反推单元格"（取每个实例的 frame 归一化即可，重叠时提示）
- **风险**：自定义模板要参与 `emptyCellIndices` 判定，需确认与内置模板走同一条代码路径

### 5. 同图多格（一个资源填多个格子）

- **行为**：允许同一资源库条目出现在多个单元格；模板填充时按"资源顺序循环"而不是"一格一图"
- **理由**：做九宫格经常是"一张主图 + 同一张图裁不同部位"，当前必须复制文件再导入
- **成本**：中。`applyTemplate` 的"一个条目一格"（规则 5）需要改成可配置；`createdSeq` 复用规则要重新定义
- **风险**：这是**改语义**，必须先在任务表里写清规则并获得确认，不能顺手改

### 6. 本地日志（工程必需，用户间接受益）

- **行为**：写 `%APPDATA%\...\logs\app.log`，轮转保留 7 天；设置里可关闭；日志只记事件与错误码，不记图片内容与路径（隐私）
- **理由**：现在导出失败只能靠用户截图。有日志才能定位"到第几条条带失败""哪张图解码失败"
- **成本**：小。Rust 侧 `tracing` + `tracing-appender`，命令失败时写一条
- **注意**：必须默认不含文件路径（隐私），只在用户主动"导出诊断包"时附带

## 三、明确不纳入 v0.2 的项

不是不重要，而是会把测试面撑爆、拖慢上面 6 项：

| 项 | 原因 |
| --- | --- |
| 文字 / 贴纸 / 水印 | 需要字体管理、选区编辑、导出字形一致性，工作量 ≥ 当前全部编辑功能 |
| 滤镜 / 调色 | 涉及色彩管理与预览一致性，与现有"预览=导出"的架构假设冲突 |
| 多画布 / 多页工程 | 文档模型要从单文档改成工程，影响撤销、导出、偏好全部 |
| 云同步 / 账号 | 与"完全离线、无遥测"的产品定位直接冲突 |
| 自动更新 | 同上；且需要签名与更新服务器 |

## 四、工程侧必须并行做的事（否则 v0.2 会带病发布）

| 项 | 当前状态 | 为什么必须做 |
| --- | --- | --- |
| asset 协议 scope 收窄（KI-11） | `$APPCACHE/**` 过宽 | 最小权限；现在 WebView 缓存目录也在 scope 内 |
| 导出峰值内存（KI-22） | 峰值 ≈ 缓冲 ×2，可达 1GB | 低配机器会失败；应把峰值纳入校验或降低上限 |
| 20,000 px 实测（T0.9） | 只有静态校验与压测，没有全链路实测 | 基线承诺的尺寸上限需要一次真实导出验证 |
| 人工验收清单自动化 | 9 个 KI 全靠人点 | v0.2 功能一多，人工回归成本会失控；建议引入 WebDriver 覆盖"导入→填空→导出"主链路 |

## 五、建议的排期（按 3 周计）

| 周 | 内容 |
| --- | --- |
| 第 1 周 | 方向键微调 + 连续填图流 + 撤销历史面板（三项都小，可并行验证） |
| 第 2 周 | 自定义模板 + 本地日志 |
| 第 3 周 | 同图多格（需先确认语义）+ 工程侧收口（KI-11/KI-22）+ 回归 |

> 如果只能做一项：做**方向键微调**。它是"能不能用来做正经排版"的分水岭，成本也最低。
> 如果能做两项：再加**连续填图流**，直接解决本轮反馈暴露的"填到第几格"心智负担。
