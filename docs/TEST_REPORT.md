## TR-01 图像解码能力验证（对应 T0.8）

**方法**：Rust 工程引入 `image 0.25.10`、`kamadak-exif 0.6.1`，程序化生成 8 类样本后逐一解码、探测格式、解析 EXIF、注入异常输入。异常用例用 `catch_unwind` 捕获 panic。

**样本**：PNG(1200×800, RGBA)、JPEG(1600×1200)、BMP(640×480)、WebP(800×600, 无损)、JPEG(8000×6000)、带 EXIF Orientation=6 的 JPEG、伪造 HEIC 签名文件、截断 PNG。

### 结果

| 用例 | 期望 | 实际 | 状态 |
| --- | --- | --- | --- |
| PNG 解码 | 成功，保留 alpha | `1200x800 color=Rgba8`，3.7 ms | 通过 |
| JPEG 解码 | 成功 | `1600x1200 color=Rgb8`，8.4 ms | 通过 |
| BMP 解码 | 成功 | `640x480 color=Rgb8`，2.7 ms | 通过 |
| WebP 解码 | 成功 | `800x600 color=Rgba8`，2.1 ms | 通过 |
| 格式探测 | 四种格式均正确识别 | `Png / Jpeg / Bmp / WebP` 全部正确 | 通过 |
| EXIF Orientation | 读出方向值 | `field=Short([6]) value=6` | 通过 |
| 无 EXIF 的 PNG | 不报错崩溃，按方向=1 处理 | 返回 `No Exif data found in PNG`，可捕获处理 | 通过 |
| HEIC 输入 | 明确拒绝，不崩溃 | 返回 `extension .heic was not recognized`，无 panic | 通过 |
| 截断 PNG | 返回错误，不崩溃 | 返回 `unexpected end of file`，无 panic | 通过 |
| 8000×6000 大图 | 可解码，记录耗时与内存 | 198.3 ms，RGBA 需 183.1 MB | 通过 |

### 关键数据

```
PNG  1200x800  →  3.7 ms   Rgba8
JPEG 1600x1200 →  8.4 ms   Rgb8
BMP   640x480  →  2.7 ms   Rgb8
WebP  800x600  →  2.1 ms   Rgba8
JPEG 8000x6000 → 198.3 ms  Rgb8  (RGBA 183.1 MB / RGB 137.3 MB)
格式支持：PNG=true JPEG=true WebP=true BMP=true HEIC=false
```

### 由数据直接推出的三个设计结论

1. **分级解码不是优化项，是必需项。** 单张 8000×6000 解码后占 183 MB；基线要求支持 50 张压力测试，若全部按原分辨率驻留内存，量级达 9 GB。因此 `ARCHITECTURE.md` §6 的"显示用小图缓存 + 导出时按需重采样"必须实现，不能作为后续优化顺延。
2. **格式探测与解码必须分两步校验。** 截断 PNG 的 `guess_format` 仍返回 `Png`（头部魔数完整），真正失败发生在解码阶段。因此导入流程不能"探测通过即认为可导入"，必须在解码失败时走跳过 + 汇总路径（基线 §6.3）。
3. **HEIC 无需额外屏蔽逻辑。** `image` 默认不含 HEIC 解码器，遇到即返回错误；只需把该错误映射为基线 §6.1 要求的中文提示（"当前不支持 HEIC/HEIF，请先转换为 JPG 或 PNG"）。

### 测试局限（须在后续补测）

| 局限 | 影响 | 补测计划 |
| --- | --- | --- |
| HEIC 样本为手工构造的 `ftyp` 签名文件，非真实 HEIC 照片 | 只验证了"识别失败不崩溃"，未覆盖真实 HEIC 的文件结构 | 若需更严格验证，取一张真实 HEIC 照片复测（v1 不支持该格式，优先级低） |
| WebP 仅测无损变体 | 未覆盖有损 WebP（VP8） | T2.x 导入实现时补一张真实有损 WebP |
| 未覆盖 CMYK JPEG、16 位 PNG、渐进式 JPEG | 真实用户图片可能出现 | 并入 T12.2 异常输入测试 |
| 未做 ICC 色彩配置验证 | 涉及"避免明显偏色"（基线 §12.5） | 并入 T10.10 |

## TR-02 依赖裁剪与回归验证（对应 T0.15）

**动机**：TR-01 的编译日志显示，`image` 默认 feature 把 `tiff`、`exr`、`avif/ravif`、`tga`、`ico`、`hdr` 等未使用编解码器全部编入，属无收益的编译耗时与解析面（攻击面）扩大。

**变更**：

```toml
image = { version = "0.25.10", default-features = false,
          features = ["png", "jpeg", "webp", "bmp"] }
```

**对比结果（`cargo clean` 后全量 release 构建）**：

| 指标 | 裁剪前 | 裁剪后 | 变化 |
| --- | --- | --- | --- |
| release 构建耗时 | 59.98 s | **21.76 s** | −64% |
| Cargo.lock 依赖包数 | 126 | **34** | −73% |
| 产出 exe 体积 | 未采集 | 1,185,792 B（约 1.13 MiB） | — |
| PNG 解码 | 3.7 ms | 3.9 ms | 持平 |
| JPEG 解码 | 8.4 ms | 7.2 ms | 持平 |
| BMP 解码 | 2.7 ms | 2.6 ms | 持平 |
| WebP 解码 | 2.1 ms | 1.4 ms | 持平 |
| 8000×6000 JPEG | 198.3 ms | 199.7 ms | 持平 |

**回归结论**：`PNG=true JPEG=true WebP=true BMP=true HEIC=false`，四种格式解码与格式探测结果与裁剪前**完全一致**，EXIF 与异常输入行为未变。**通过**。

> 结论：P1 正式工程直接采用该 feature 配置，不保留默认全开。

## TR-03 画布引擎装配验证（对应 T0.14）

**目的**：验证「`DocumentState` → `SceneDescriptor` → Konva 投影」这条数据流的正确性与 50 实例下的帧预算。

**方法**：构建一个 Tauri 2 探测应用（React + Konva 10.9.0），在**真实 WebView2 运行环境**中执行基准，结果由 Rust 命令写入 JSON 落盘，不以截图或肉眼判读为准。

**条件**：文档画布 2400×1600，视图缩放 50%（Stage 1200×800），50 个实例（每个 400×300 带渐变纹理的占位位图），`devicePixelRatio = 2`。

### 结果

| 指标 | 数值 | 说明 |
| --- | --- | --- |
| 运行时 | WebView2 / Chromium 155（`Edg/155.0.0.0`） | 真实目标运行时 |
| Konva 版本 | 10.9.0 | — |
| 派生耗时（状态→场景描述） | avg **0.01 ms**，p95 0.1 ms，max 0.1 ms | 50 实例下可忽略 |
| 首屏完整渲染 | **5.3 ms** | `layer.draw()` 同步绘制 50 张图 |
| 场景 A 直接改节点 | avg 0.04 ms | 见下方"测量缺陷" |
| 场景 B 完整管线 | avg 0.11 ms | 见下方"测量缺陷" |
| **实际帧间隔** | **17.3 ms → 57.8 fps** | **本项最可信的性能指标** |
| 节点数 | 50 | 与实例数一致 |

### 正确性断言（4/4 通过）

| 断言 | 结果 |
| --- | --- |
| 节点数等于实例数（50） | 通过 |
| 节点顺序与实例数组顺序一致（首尾校验） | 通过 |
| 首个节点几何与文档状态一致 | 通过 |
| 管线更新后节点位置与状态同步（误差 < 0.001 px） | 通过 |

### 结论

1. **数据流成立。** "状态为真相、Konva 为投影"的设计在真实运行时可用，diff 更新不影响顺序与几何正确性。
2. **派生层零负担。** 50 实例派生 0.01 ms，说明每次交互全量重新派生是安全的，不必为性能引入增量派生或记忆化。**这将显著简化状态管理实现。**
3. **50 实例交互不掉帧。** 每帧在完成"派生 + diff 应用 + 重绘"的前提下，帧间隔 17.3 ms（理想 16.7 ms），无成片掉帧。基线 §14.2 要求"典型 2–10 张、压测 50 张时拖动缩放保持可用"**初步达成**。
4. **首屏 5.3 ms** 意味着资源库导入后一次性重建场景无需分帧处理。

### 测量缺陷（必须记录，不得据此夸大性能）

`layer.batchDraw()` 是**延迟绘制**，它只是把重绘排入下一帧。因此场景 A/B 测得的 0.04 ms / 0.11 ms **只是入队耗时，不是真实光栅化耗时**；表中"estFps 25000 / 9090"这类推算值**无意义，不予采用**。

真实绘制成本由 `layer.draw()` 的 5.3 ms（同步）与帧间隔 17.3 ms 反映。后续如需精确到"每帧光栅化耗时"，应在正式应用里用 Chrome Tracing / Performance 面板采样，而不是在基准里推算。**此项列为 T3.7 的实现要求。**

### 本次未覆盖（属 T0.9 / T3.7 范围）

- 100% 缩放与 200% 缩放下的绘制成本（本次固定 50%）。
- 真实照片位图（本次为 Canvas 占位图，未含大尺寸解码数据）。
- 裁剪、圆角、边框、透明度混合叠加后的绘制成本。
- 导出条带渲染路径。

## TR-05D 画布渲染链路（对应 T3.2 / T3.4 / T5.1）

### 分层落地

```
DocumentState（真相）
   ↓ deriveScene（纯函数，不 import Konva）
SceneDescriptor（节点数组，含 frame/crop/rotation/opacity）
   ↓ syncLayer（唯一 import Konva 的适配器）
Konva 节点树（投影，可整体重建）
```

`eslint` 的边界规则保证只有 `features/scene/**` 能 import Konva，本阶段新增的 `derive.ts` / `apply.ts` / `KonvaStage.tsx` 全部落在这个目录内。

### 新增自动化用例

| 文件 | 用例数 | 覆盖的关键契约 |
| --- | --- | --- |
| `domain/transform.test.ts` | 10 | `coverCrop`：宽裁/高裁/比例一致不裁；**不回写传入的 crop**；旋转 90 后按互换后的宽高裁；零尺寸返回 scale=0；`alignFrame` 整数对齐 |
| `domain/layout.test.ts` | 9 | `centerFitFrame` 等比居中；`gridFrames` 结果可预测（无随机）、互不重叠、全部落在画布内、保持各自宽高比 |

前端用例总数 46 → **65**（transform 10 / geometry 14 / layout 9 / document 19 / library 13）。

### 三条实现决策

| 决策 | 理由 |
| --- | --- |
| `coverCrop` 只读 crop，适配裁切不写回 | 用户裁剪与适配裁切是两层；混写会导致切换模板后丢失用户裁剪（ARCHITECTURE §4） |
| 内容层用 `layer.clip()` 裁到画布边界 | 基线 §5.3 / §10.2：边界外内容在视图与导出中同样被裁切，不自动扩张画布 |
| 未加载完成的图像直接跳过渲染 | 宁可暂时不画，也不要先按错误尺寸画上去再跳变；跳过数量在工具条显示为"N 张加载中" |

| 项 | 原因 |
| --- | --- |
| 画布实际渲染效果 | 空状态下不挂载 Konva 舞台，需导入图片并双击放入才能看到；无法自动化 |

## TR-05E 画布渲染性能基准（对应 T3.7）

**方法**：在 release 版应用内运行真实渲染管线（`deriveScene → syncLayer → layer.draw()`），用**同步 `layer.draw()`** 计时，而不是 `batchDraw()` 的入队耗时（KI-04 的坑）。基准由 `%TEMP%\pintu_bench.flag` 触发，结果写入 `%TEMP%\pintu_canvas_bench.json` 后自动退出——无需人工观察。

**条件**：50 个实例、文档画布 2400×1600、视口 1440×836、`devicePixelRatio = 2`、WebView2 / Chromium 155、Konva 10.9.0。

### 结果

| 缩放 | 管线每帧（含派生+适配+绘制） | 纯绘制 | 60Hz 预算占用 |
| --- | --- | --- | --- |
| 适应画布（0.522×） | avg **0.72 ms** / p50 0.7 / p95 **1.2** / max 1.6 | avg 0.35 / p95 0.6 | **7.2%** |
| 100% | avg **0.72 ms** / p50 0.7 / p95 **1.1** / max 1.1 | avg 0.25 / p95 0.4 | **6.6%** |

- 整体重建（销毁全部节点 + 重建 50 个）：**2.5 ms**
- 管线额外开销（派生 + 适配 diff）≈ 0.37–0.47 ms／帧

### 结论

1. **架构的间接层可承受。** "状态→场景描述→Konva 投影"三级数据流每帧只多花约 0.4 ms，占 16.7 ms 预算的 2.4%。这一层带来的可测试性与可重建性，成本可以忽略。
2. **50 实例远未触顶。** p95 仅占预算 7%，余量充足；基线 §14.2「50 张时拖动缩放保持可用」达成。
3. **模板切换不会卡顿。** 整体重建 2.5 ms，即便模板切换走"全量重建"路线也来得及。

### 本基准不覆盖

- **导出光栅化**：这里测的是 1440×836 视口（DPR2 = 2880×1672 后备缓冲），与 20,000 px 导出不在一个量级，不能外推（T0.9 / T12.4 负责）。
- **真实照片位图**：基准用 480×360 合成图，未含大图解码后的纹理上传成本。
- **裁剪/圆角/边框叠加**：这些在 P7 才实现，届时需复测。

## TR-05F 撤销/重做（对应 T4.1~T4.4）

### 模型

快照式历史栈（ADR-0004）：`past` 存变更前快照，`future` 存被撤销掉的状态。深度上限 100，新编辑清空 redo 分支。

合并窗口：`commit(recipe, { mergeKey })` 中同一 key 且 1200ms 内连续提交不新建步骤，`endMerge()` 显式结束。

### 新增用例

| 文件 | 用例数 | 覆盖的关键契约 |
| --- | --- | --- |
| `domain/history.test.ts` | 11 | 入栈/撤销/重做；撤销到底返回 null；新编辑清空 redo；超上限丢最旧；`nextUndoLabel` |
| `state/docStore.test.ts` | 14 | 无变化不产生步骤也不置脏；**50 帧拖动只占 1 个撤销步骤**；撤销一次回到拖动前；不同 mergeKey 开新步骤；`endMerge` 后开新步骤；`commitNoHistory` 改文档但不入栈 |

前端用例总数 65 → **90**。

### 关键用例的实际含义

| 用例 | 为什么重要 |
| --- | --- |
| 50 帧拖动只占 1 步 | 若按帧入栈，用户撤销一次只退回一帧，实际不可用 |
| 撤销一次回到拖动前 | 验证合并没有把"第一帧"当成步骤边界 |
| `endMerge` 后开新步骤 | 验证显式结束优先于时间窗，避免跨操作合并 |
| `commitNoHistory` 不入栈 | 基线 §11.2：资源释放不可撤销，撤销时不能"复活"关联实例 |
| recipe 返回同一引用时不置脏 | 避免无变化的提交污染历史与"未导出修改"标记 |

## TR-05G 画布交互：命中、拖动、选中、删除（对应 T5.4 / T5.5 / T6.1 / T6.8）

### 交互链路

```
pointerdown → 屏幕坐标转画布坐标 → hitTest（顶层优先）→ 更新选中
            → 若命中则进入拖动，记录起点
pointermove → 增量提交 commit(updateInstance, { mergeKey: "drag:<ids>" })
pointerup   → endMerge()（下一次拖动必然开新撤销步骤）
```

**坐标换算**：`docX = (clientX - hostLeft - panX) / zoom`。命中判定直接用 `frame` 矩形包含——因为 ADR-0003 决策四规定 frame 是轴对齐显示框，旋转只作用于内容，所以无需对旋转做额外几何变换。

### 新增用例

| 用例 | 覆盖的契约 |
| --- | --- |
| `hitTest` 命中最顶层 | 数组顺序即图层顺序，重叠时取后加入者 |
| `hitTest` 边界点命中 | 含边界，避免边缘 1px 点不中 |
| `hitTest` 空文档返回 null | 空状态不崩 |
| `filterAliveSelection` 清理失效选中 | 实例被删/被级联删除后，选中集合不残留幽灵 id |
| `filterAliveSelection` 保持顺序 | 多选顺序不因清理而乱 |

前端用例总数 90 → **95**。

### 关键实现约束

| 约束 | 原因 |
| --- | --- |
| 事件回调与最新 doc/view 放入 `useRef` | 事件处理器只在挂载时绑定一次；闭包捕获旧值会导致"第二次拖动回到旧位置"这类难查问题 |
| 拖动增量而非绝对位置 | 多选拖动时每个实例各自累加，避免"以鼠标为中心重排" |
| `pointerup` 必须调 `endMerge()` | 否则下一次拖动会并入上一步（ADR-0004 决策三） |
| 数值编辑 Enter/失焦才提交 | 否则每敲一个字符就产生一个撤销步骤 |
| 数值输入 Esc 回滚 | 与基线 §11.1「Esc 优先取消当前编辑」一致 |
| 控制点尺寸按 `zoom` 反向补偿 | 手柄在屏幕上恒为 7px；否则放大视图时手柄巨大、缩小后点不中 |
| 控制点命中优先于实例命中 | 否则点在手柄上会变成"选中/拖动图片" |

### 控制点缩放（T5.4 后半）

| 用例 | 覆盖的契约 |
| --- | --- |
| `handlePoints` 方位齐全 | 八个控制点，角点在四角、边点在边中点 |
| 拖右边只改宽度 | 左边固定 |
| 拖左边改 x | 右边保持不动（`x + w` 不变） |
| 拖上边改 y | 下边保持不动 |
| 拖右下角 | 左上角固定，宽高同变 |
| 拖左上角 | 右下角固定，x/y/w/h 同变 |
| 最小尺寸限制 | 拖到反向不会出现零或负尺寸（否则 `coverCrop` 会除零） |
| `cursorForHandle` | 角点/边点给出正确缩放指针 |

缩放几何放在 `domain/transform.ts`，绘制（`apply.ts`）与命中（`KonvaStage`）共用同一组坐标计算——两处各算一遍必然出现"手柄画在这里、点击判定在那里"的错位。

### 关键实现约束

| 约束 | 原因 |
| --- | --- |
| 模板存归一化坐标 | 画布尺寸可改，写死像素会让全部模板失效（ADR-0007） |
| 像素换算按边取整 | 位置与尺寸各自取整会产生 1px 缝或重叠 |
| 复用只改 frame | 图像级属性必须原样保留（基线 §9.4 第 8 条） |
| 分组键是条目 id 而非路径 | 同路径"再次添加"的条目必须独立复用（第 4 条） |
| `containCrop` 只读 crop | 切换适配模式不得改写用户裁剪 |
