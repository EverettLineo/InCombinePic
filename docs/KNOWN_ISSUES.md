# 已知问题清单

- 版本：v0.1（P0 阶段）
- 更新规则：新增问题须含**复现步骤、影响范围、规避方式、是否影响发布**（基线 §14.3、§18.2）
- 当前阶段尚无应用代码，故无功能缺陷；以下为验证阶段暴露的工程问题与限制

## 分级约定

| 级别 | 定义 | 发布要求 |
| --- | --- | --- |
| 阻断性 | 无法启动、核心流程不可用、频繁崩溃 | 发布前必须为零 |

## KI-01（已关闭）`image` 默认 feature 全开

- **现象**：编译拉入 tiff / exr / avif / tga / ico / hdr 等未使用编解码器，依赖 126 个、构建 60s
- **处理**：改为 `default-features = false`，仅启 png/jpeg/webp/bmp
- **结果**：依赖 34 个、构建 21.76s、四格式解码行为一致（TR-02）
- **状态**：已关闭（2026-10-27）

- **影响发布**：否

## KI-04（已关闭）基准测量的语义陷阱

- **现象**：`layer.batchDraw()` 为延迟绘制，其返回耗时只是"入队耗时"，不是光栅化耗时
- **风险**：若据此推算 FPS 会得出荒谬结论（如 25000 fps）
- **处理**：T3.7 改为在应用内用同步 `layer.draw()` 计时，并落盘基准结果（见 TEST_REPORT TR-05E）
- **已固化**：`task.md` T3.7 明确要求"不得用 batchDraw 入队耗时推算"
- **状态**：已关闭（2026-10-29）

## KI-05 HEIC 拒绝的验证深度不足

- **规避**：v1 明确不支持该格式，仅需错误提示正确
- **计划**：若后续用户反馈，补真实样本复测
- **影响发布**：否

## KI-12 三入口交互未经人工实操验证

- **范围**：拖放文件、`Ctrl+V` 粘贴图片、拖拽排序、释放/清空的原生确认框
- **原因**：均需真实鼠标键盘操作与系统剪贴板状态，当前无法自动化
- **已做的风险收敛**：
  - 三个入口共用同一 `importPaths`，选择器入口一旦验证通过，另两个的逻辑分支风险很低
  - 粘贴仅在剪贴板确有图片时才拦截，且可编辑控件内直接放行（避免抢走文本粘贴）
  - 列表排序用指针事件而非 HTML5 拖拽，规避了 Windows 上的原生拖放冲突（D-004）
- **计划**：一次性人工走查后关闭
- **影响发布**：**是** —— 基线 §1.3 成功标准第 1 条要求三种入口可用，需实操确认

## KI-09 缩略图实际渲染未经肉眼确认

- **影响发布**：否

## KI-11 asset 协议 scope 偏宽

- **现象**：`app.security.assetProtocol.scope` 设为 `$APPCACHE/**`，而 WebView 自身的数据目录 `EBWebView` 也在该根目录下（启动后已实测存在）
- **影响**：理论上 WebView 页面可读取自身缓存/存储目录。对本应用（本地单窗口、无外部内容）风险很低，但不属最小权限
- **为何没当场收窄**：更精确的 `$APPCACHE/thumbnails/**` 无法在当前条件下验证是否被 scope 解析器接受，一旦不生效会导致缩略图全部加载失败且难以察觉。**宁可先保持已确认可用的写法，把收窄留到可验证的时机**
- **计划**：T12.x 安全收口时收窄 scope，并配合人工验证缩略图仍能显示
- **影响发布**：否（需在发布前完成收窄与验证）
