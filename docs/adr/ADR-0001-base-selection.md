# ADR-0001：开源基座与技术栈选型

- 状态：**已接受（2026-10-27 用户确认）**
- 日期：2026-10-27
- 决策人：用户 + 架构师（Agent）
- 依据：`图片拼接工具_工程需求基线_v1.16.md`、`docs/OPEN_SOURCE_SURVEY.md`、T0.5 构建实测、T0.8 解码实测

---

## 1. 背景

需求基线要求先调研可复用开源项目、再定技术栈，且不得把"目标平台"写成"已验证平台"。已完成两件事：

1. **T0.5 实测**：Tauri 2 + React + TS 在全链路可构建、可打包，产出 exe + MSI + NSIS（1.39 MiB）。
2. **开源调研**：完成 L1（整体应用）/ L2（编辑器内核）/ L3（图像处理）三层筛选，全部许可证经 API 与 LICENSE 原件核实。

核心矛盾：用户希望"选定合适基础后在其之上继续开发"，但调研结论是 **L1 不存在值得 fork 的基座**。因此必须明确"基础"落在哪一层。

---

## 2. 决策

### 决策一：基座采用「组合式基座」，不 fork 任何现成拼图应用

**基座 = Tauri 2 官方 `react-ts` 模板（工程骨架）+ Konva（画布引擎）+ Rust 图像管线（处理内核）。**

否决 fork 的四点理由（详见调研报告 §2）：

| 否决原因 | 具体表现 |
| --- | --- |
| 功能模型缺口是"层"而非"点" | 候选项目缺的是画布文档模型、命令历史、图层系统、模板引擎，不是某个功能 |
| 技术栈冲突 | Electron+Svelte / Qt C++ / PyQt，均与已验证的 Tauri+React 冲突 |
| 复用率低于重写成本 | 需剥离的部分多于保留的部分，还要背上他人目录结构与历史包袱 |
| 社区规模不可依赖 | 0~6 star、单次提交的练习级项目，长期只能自己维护 |

> 这是本次决策最需要用户知情的部分：**"在开源之上开发"在本项目实现的形态是"在成熟库之上开发"，而不是"在成熟 App 之上改"。**

### 决策二：Konva 只做渲染投影，文档状态是唯一真相

绝不把 Konva 的节点树当作业务数据源。数据流固定为：

```
DocumentState（不可变，纯数据）
   ↓ 派生
SceneDescriptor（纯计算，无 Konva 类型）
   ↓ 适配层
Konva 节点树（视图投影，可随时整体重建）
```

**理由**：撤销/重做要求状态可深比较、可快照、可回放（基线 §11.2）。若以 Konva 节点为真相，历史栈会与视图生命周期纠缠，出现"撤销后节点复用了错误引用"这类难查缺陷。此条是硬约束，不因实现便利性妥协。

**代价**：需要写一层适配器把 `SceneDescriptor` 映射到 Konva，且拖动过程中的高频更新要走"命令 → 状态 → 重绘"而非直接改节点。这部分成本已在评估中计入。

### 决策三：导出采用「条带化渲染 + Rust 编码」，不用单一巨型 Canvas

20,000 × 20,000 RGBA 约 1.6 GB，WebView2 的 Canvas 面积上限与内存都无法承载。方案：

1. 前端按固定条带高度（初值 2048 px）逐条渲染，每条复用同一套 Konva 渲染路径（保证与预览同一渲染器、同一几何语义）。
2. 每渲染完一条，把该条位图交给 Rust，追加写入编码器，随后释放该条 canvas。
3. Rust 侧使用 `fast_image_resize` 做高质量重采样，`image` 做编码，并统一清除元数据。

**理由**：既不引入"前端一套渲染器、Rust 又一套渲染器"的双实现一致性风险（基线 §4.1 的核心红线），又把峰值内存压到单条带量级（20,000 × 2048 × 4B ≈ 164 MB）。

---

## 3. 备选方案与放弃理由

| 方案 | 放弃理由 |
| --- | --- |
| fork `chututu`（Electron+Svelte，MIT） | 技术栈冲突；缺画布/图层/撤销全层；Svelte 生态与已验证的 React 链不兼容 |
| fork `QuickImageMerge`（Qt C++，MIT） | 放弃前端生态，UI 效率低；同样缺核心层 |
| fork `image-stitcher`（纯 Web，MIT） | 无桌面壳、无图层、无撤销；练习级规模 |
| Fabric.js 替代 Konva | 功能过剩（SVG 解析/滤镜），bundle 更大，460 个 open issue；无原生 `crop` 语义 |
| 从零自研画布引擎 | 可控性最高，但等于重写 Konva 的全部交互与变换逻辑，工期与缺陷风险不可接受 |
| 前端单 canvas 直接导出 | 20,000 px 不可行，无法满足基线 §12.2 尺寸目标 |

## 4. 后果

### 正面

- 许可证全部为 MIT / Apache-2.0 / BSD-2-Clause：**无 GPL/AGPL 传染，闭源分发成立**。
- 画布交互（选择、变换、图层、吸附）直接获得成熟实现，工期重心可放在产品语义上（模板、资源库生命周期、预览导出一致性）。
- 文档模型自持，撤销/重做与未来"项目文件"能力不被第三方库绑架。
- 条带化导出为 20,000 px 提供了工程上可行的路径。

### 负面 / 需承担的风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Konva 适配层是自研代码 | 约 1 个模块的开发量，且需覆盖高频拖动性能 | P3 阶段先做渲染适配最小闭环并测帧率（T3.7） |
| 条带渲染的接缝问题 | 条带边界可能出现 1px 错位或抗锯齿差异 | 条带按整数像素对齐 + 边界重叠 1px 采样；T10.11 差分测试必测 |
| `exif-rs` 维护频率低 | 罕见 EXIF 变体解析异常 | T0.8 覆盖常见机型样本；异常时降级为"忽略方向"并提示 |
| 显示分辨率与导出分辨率分级解码 | 若实现不当会出现"预览清晰、导出模糊"或反之 | 统一由 Rust 按目标尺寸重采样；预览与导出共用同一 `cover` 计算函数 |
| Konva 的 `NOASSERTION` 元数据 | 合规工具可能误报 | 已在第三方声明中直接引用 LICENSE 原件文本 |

### 合规义务（必须落地，非可选）

1. 应用内提供「关于 → 第三方开源许可」页面，列明 Konva（含 KineticJS 版权段）、Tauri、`image`、`fast_image_resize`、`exif-rs` 的许可证全文或链接。
2. Apache-2.0 组件需在分发物中附 NOTICE 文件。
3. 禁止引入 `miniPaint` 代码（许可证未核验）；禁止引入任何 GPL/AGPL 组件。

---

## 5. 复核触发条件

出现以下任一情况，必须重开本 ADR，不得静默偏离：

1. Konva 无法满足某项基线要求（例如吸附/变换的精度或性能不达标），需回退 Fabric 或自研。
2. T0.9 实测证明条带化导出在 20,000 px 下仍不可行 → 需下调尺寸上限（属产品行为变更，基线 §19 要求用户确认）。
3. 需要引入 GPL/AGPL 组件 → 直接阻断，须用户决策分发模式。
4. 分发模式从闭源改为开源，或反之。

## 6. 确认结论（2026-10-27）

| 编号 | 事项 | 用户决定 | 落地影响 |
| --- | --- | --- | --- |
| Q-1 | 是否接受"组合式基座、不 fork 现成拼图应用" | **接受** | 进入 P1，按 `docs/ARCHITECTURE.md` 装配 |
| Q-2 | 分发模式 | **开源** | 自有代码用 MIT，见 `ADR-0002-license.md`；须保留第三方许可声明 |
| Q-3 | 20,000 px 实测不达标时的处理 | **直接下调上限** | 不保留"警告后继续"的软路径；T0.9 / T12.4 实测后直接把新上限写入基线与导出面板 |

> Q-3 的影响需要明确：由于选择"直接下调"，一旦实测证明某尺寸不可行，**导出面板将直接拒绝该尺寸并给出新上限**，而不是"警告后仍允许用户冒险导出"。这比基线的建议默认值更严格，属产品行为收敛，已记录在案；若后续希望放宽，须走基线 §19 变更流程。
