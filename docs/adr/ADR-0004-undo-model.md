# ADR-0004：撤销/重做采用快照模型，且提前到编辑功能之前实现

- 状态：**已接受**
- 日期：2026-10-29
- 决策人：架构师
- 相关：`docs/ARCHITECTURE.md` §8、`task.md` P4

---

## 1. 背景

需求基线 §3 阶段 C 把撤销/重做排在第 9 步（在放置、变换、图层、裁剪、模板之后）。但本项目的编辑操作从 P5 才开始产生，若按原顺序，P5~P8 的所有编辑调用点都要在 P9 回头补历史逻辑。

## 2. 决策

### 决策一：撤销基座前移到所有编辑功能之前（已执行于 P4）

**理由**：撤销模型决定编辑操作的数据流形态。如果先写编辑、再补历史，只有两种结果——要么每个调用点改一遍，要么把历史逻辑分散到各处（后续必然遗漏）。前移的成本只是一次设计，后移的成本是返工。

**依据**：基线 §3 明确"实际顺序可在 ADR 中说明调整理由"，本 ADR 即该说明。

### 决策二：采用快照模型，不做命令回放

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| 命令回放（记录操作序列，撤销时反向执行） | 内存占用小 | 模板切换、级联删除这类跨多对象操作要写反向逻辑，极易不完整；一旦漏一个字段就是"撤销后状态不对" | 否决 |
| **快照（记录变更前后的完整文档状态）** | 天然原子，任何操作都能精确还原；实现简单，不易漏 | 内存占用高于回放 | **采纳** |

**内存评估**：文档状态是纯数据，快照间大量对象共享引用（未变实例复用同一对象）。50 实例、历史上限 100 步的实际增量远小于"100 × 全量副本"。上限 100 步（基线允许设上限，见 ARCHITECTURE §8）。

### 决策三：合并窗口用显式 `mergeKey`，不靠时间猜测

连续拖动每帧都会提交一次，但用户只应撤销一次。实现为：

```ts
commit(recipe, { label: "拖动图片", mergeKey: "drag:inst-abc" })
```

- 同一 `mergeKey` 且在 1200ms 内的连续提交 → 不新建历史步骤
- 交互结束时调用 `endMerge()`，下一次提交必然开新步骤
- 没有 `mergeKey` 的提交（如放置图片）每次都独立成步

**为什么同时要时间窗和显式结束**：只靠时间窗，用户拖到一半停手两秒再拖，会被切成两步（体验错误）；只靠显式结束，任何忘记调用的路径都会把后续所有编辑合并成一步（更糟）。两者并用，显式结束为主、时间窗兜底。

## 3. 后果

### 正面

- P5 之后的编辑功能只需 `commit(recipe, opts)`，不关心历史
- 模板切换的原子撤销（基线 §9.4 第 9 条）天然满足——它就是一次快照
- 撤销/重做实现与 UI 解耦，按钮与快捷键共用同一入口

### 负面 / 风险

| 风险 | 缓解 |
| --- | --- |
| 忘记传 `mergeKey` 导致拖动产生上百步 | 单个交互内统一传同一个 key；`docStore` 用例覆盖"50 帧只产生 1 步" |
| 忘记调 `endMerge()` 导致跨操作合并 | 1200ms 时间窗兜底；拖动类交互在 pointerup 时必须调用 |
| 快照内存随实例数增长 | 历史上限 100；结构共享；若实测吃紧可改为"仅存差异字段" |

### 合规约束

- 资源库操作（导入/释放/清空）**不得**经 `commit`，必须走 `commitNoHistory`（基线 §11.2）
- 该约束已用用例固化：`commitNoHistory` 改变文档但 `past` 长度不变

## 4. 复核触发条件

1. 若出现"撤销后状态与预期不一致"的缺陷 → 优先怀疑某个编辑路径绕过了 `commit`
2. 若实测内存占用过高（历史上限 100 步时增量 > 200 MB）→ 改为差异快照
3. 若需要"撤销跨会话保留" → 与基线 §11.2「历史只存在于当前会话」冲突，须先改基线
