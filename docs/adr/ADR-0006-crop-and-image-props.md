# ADR-0006：裁剪锁定格子比例、边框画在内侧、坐标按位图比例换算

- 状态：**已接受**
- 日期：2026-10-30
- 决策人：架构师
- 相关：`src/domain/crop.ts`、`src/domain/transform.ts`、`src/features/scene/apply.ts`、`task.md` P7

---

## 1. 背景

P7 要落地裁剪、透明度、边框、圆角。基线只写了"支持通过裁剪框控制点拖动调整""默认无边框无圆角"，没有定义三件会长期影响正确性的事：

1. 裁剪框是否允许任意宽高比？
2. 边框画在显示框内侧还是外侧？
3. `crop` 存源图像素，但渲染用的是降采样位图——坐标怎么对齐？

第 3 条在实现前被当成"顺手写一下"，实际是一个会让所有大图渲染错误的陷阱。

## 2. 决策

### 决策一：`crop` 永远存源图像素，与旋转完全解耦

- 旋转只改 `rotation`，**从不重写 `crop`**；
- `coverCrop` 在显示时按格子比例做二次裁切，但**只读不写**（P3 已定）；
- 因此"旋转 90° → 裁剪 → 转回 0°"能完整保留裁剪数据（用例锁定）。

若把裁剪存成"旋转后的坐标"，每次旋转都要换算一次，来回转两次就会因取整累积误差丢像素，且无法判断数据是否被修改过。

### 决策二：裁剪框锁定为格子比例

| 方案 | 行为 | 结论 |
| --- | --- | --- |
| 允许任意比例 | 用户裁成 1:1，放进 3:2 的格子后仍会被 `coverCrop` 二次居中裁切，所见非所得 | 否决 |
| **锁定为"旋转后正好等于 frame 比例"** | 裁完即所见，二次裁切退化为无操作 | **采纳** |

比例计算：`cropAspectFor(frame, rotation)`。旋转 90/270 时宽高互换，比例取倒数——否则旋转后裁剪框与格子对不上。

代价：用户不能"裁成任意形状再留白"。本工具的格子由模板/布局决定，填满语义下留白没有意义。

### 决策三：裁剪编辑器是独立浮层，展示完整源图

画布上显示的是"裁剪 → 填满格子"的**结果**。在结果上再叠一层裁剪框，用户拖动时看到的是被二次裁过的画面，反馈会很怪，也无法框到当前不可见的区域。

浮层里展示完整源图，框住的就是真正的源图像素区域；编辑器内部用归一化坐标（0~1），因此换更清晰的预览图不改变结果。

### 决策四：边框画在显示框**内侧**

格子是拼接的基本单元，边框若向外画会压到相邻图片，且相邻两图的边框会叠成双倍宽。内侧绘制配合圆角时，描边路径按 `半径 - 线宽/2` 收缩，视觉上与外轮廓同心。

### 决策五：crop（源图像素）→ 位图坐标必须按比例换算

显示用的位图是 `prepare_thumbnail` 降采样后的预览图（最长边 2048），而 `crop` 是源图像素。直接把 4000px 宽的 crop 交给 2048px 宽的位图，Konva 会采样到图像外。

实现为 `toImageCrop(crop, pixelScale)`，`pixelScale = 位图宽 / 源图宽`，由图像源携带（`SceneImage.pixelScale`）而不是在渲染层反推。

**这是一处已存在的真实缺陷**：P3 起渲染就带着这个问题，只是当时 `crop` 恒为全图，且画布从未被肉眼确认（KI-13），所以没有暴露。若不修，P7 一旦允许裁剪，所有超过 2048px 的照片都会整张空白或错位。

## 3. 后果

- 裁剪、旋转、翻转、透明度、边框、圆角全部落在 `CanvasInstance` 的独立字段上，互不覆盖原始像素（基线 §8.3）。
- 所有属性修改都走 `commit`，天然进撤销栈；滑块与取色器用 `mergeKey` 合并为一步。
- 圆角靠 Konva `Group` 的 `clipFunc` 实现——`Konva.Image` 是 Shape 不是容器，无法裁剪自身，因此实例的节点结构从"单个 Image"改为"Group(Image + Border Rect)"。
- 导出（P10）必须复用 `coverCrop` + `toImageCrop` + 同样的内侧边框与圆角规则，否则预览与导出会不一致（基线 §12.6）。
